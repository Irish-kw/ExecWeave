# Анализ безопасности

ExecWeave включает консервативный, объяснимый слой правил поверх завершённого графа выполнения.

```bash
execweave analyze run.graph.json
```

Записать тот же отчёт в файл:

```bash
execweave analyze run.graph.json --output analysis.json
```

Текущая версия схемы анализа — `0.2`.

## Цель

Слой анализа приоритизирует доказательства графа для проверки. Он не утверждает, что агент вредоносен только потому, что тот обращался к чувствительному ресурсу или устанавливал сетевое соединение.

Основное правило:

> **Не превращать совместное наблюдение или происхождение процессов в утверждение о потоке данных.**

## Текущие правила

### Доступ к чувствительным файлам

Правило ищет файловые рёбра, связанные с распространёнными чувствительными путями или именами файлов, например:

- `~/.ssh/*`
- `~/.aws/credentials`
- `~/.kube/config`
- конфигурация Docker
- `.npmrc`
- `.pypirc`
- `.netrc`
- `.env`
- распространённые имена приватных SSH-ключей

Каузальное процессное ребро, подтверждённое системным вызовом, является более сильным доказательством, чем некаузальное наблюдение уровня сессии.

### Внешний сетевой контакт

Правило идентифицирует рёбра процессов к внешним сетевым endpoints, исключая очевидные loopback/private/link-local адреса.

Текущая runtime-телеметрия в основном работает с IP endpoints. Корреляция DNS/доменов — будущая работа.

### Возможный путь чувствительный файл → сеть в одном процессе

Если **один и тот же процесс** имеет каузальные доказательства доступа к чувствительному файлу, а затем более позднюю каузальную внешнюю сетевую активность, ExecWeave создаёт finding для приоритизации.

```text
process
  ├── OPENED_READ ──→ ~/.ssh/id_ed25519
  └── CONNECTED_TO ─→ 8.8.8.8:443
```

Finding содержит:

```json
{
  "data_flow_proven": false,
  "exfiltration_proven": false
}
```

Граф доказывает, что процесс выполнил оба действия в таком хронологическом порядке. Он **не доказывает**, что байты из файла были отправлены через соединение.

### Возможный делегированный путь чувствительный файл → сеть

Схема анализа `0.2` также следует по хронологическим каузальным рёбрам `SPAWNED`.

Пример:

```text
parent process
  ├── OPENED_READ ──→ ~/.ssh/id_ed25519
  └── SPAWNED ──────→ child process
                         └── CONNECTED_TO ─→ external endpoint
```

Делегированный finding создаётся только если:

1. ребро доступа к чувствительному файлу каузально;
2. ребро или цепочка `SPAWNED` каузальны;
3. последовательность spawn происходит после последовательности доступа к чувствительному файлу;
4. внешнее сетевое доказательство потомка происходит после цепочки spawn;
5. глубина пути остаётся в пределах консервативного ограничения обхода анализатора.

Это доказывает хронологический путь происхождения процессов. Но всё ещё **не доказывает**, что дочерний процесс получил данные файла от родительского.

Делегированные findings явно записывают:

```json
{
  "causal_process_lineage": true,
  "data_inheritance_proven": false,
  "ipc_proven": false,
  "data_flow_proven": false,
  "exfiltration_proven": false
}
```

`SPAWNED` — доказательство создания/происхождения процесса, а не доказательство наследования памяти, записи в pipe, передачи через socketpair, shared memory, передачи секрета через окружение или какого-либо другого конкретного перемещения данных.

Реальные утверждения о потоке данных или эксфильтрации требуют более сильных доказательств, например taint tracking, provenance с учётом IPC или побайтовой телеметрии read/write/network.

## Уровень важности

Значения severity — это уровни приоритизации, а не оценки уязвимости:

- `high`
- `medium`
- `low`
- `info`

Текущие примеры:

- только внешнее соединение: информационный сигнал;
- доступ к чувствительному файлу: зависит от отношения и силы атрибуции;
- чтение чувствительного файла в том же процессе, за которым следует подтверждённое внешнее соединение: сигнал высокого приоритета;
- делегированный путь через дочерний процесс: ниже эквивалентного пути в одном процессе, поскольку передача данных через границу процессов не доказана.

## Зависимость от backend

Качество анализа ограничено качеством сборщика.

Эталонный Linux-backend `strace` может предоставлять атрибутированные процессам доказательства системных вызовов для поддерживаемых операций. Переносный backend имеет более слабую атрибуцию файловой системы и поэтому не может подтверждать те же выводы на уровне процессов.

Анализатор соблюдает метаданные `causal` графа, а не повышает более слабые доказательства.

## Вывод

Отчёт содержит:

- версию схемы анализа
- идентификатор сессии
- общее количество findings
- количества по severity
- явные ограничения
- идентификатор правила для каждого finding
- заголовок и сводку
- связанные идентификаторы узлов
- связанные идентификаторы рёбер
- идентификаторы событий-доказательств
- атрибуты конкретного правила

Делегированные findings дополнительно содержат цепочку процессов, количество шагов делегирования, spawn-последовательности и явные отрицательные гарантии относительно наследования данных/IPC/потока данных.

## Будущие слои анализа

Возможные дополнения:

- разрешение сущностей credentials и secrets
- DNS/domain-корреляция и контекст
- явные IPC-рёбра
- provenance переменных окружения и унаследованных handles
- семантический контекст agent/tool/MCP
- обнаружение аномалий
- ранжирование путей атаки
- побайтовый data-flow / taint tracking
- runtime-политика allow / warn / block

Эти расширения должны сохранять различие между наблюдаемыми доказательствами, выведенным риском, происхождением процессов и доказанным каузальным потоком данных.
