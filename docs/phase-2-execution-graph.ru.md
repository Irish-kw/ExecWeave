# Фаза 2 — Граф выполнения

Фаза 2 преобразует валидированный JSONL-поток событий Фазы 1 в постоянный граф выполнения, который можно запрашивать и впоследствии визуализировать локальным интерфейсом.

## Текущее состояние

Первое ядро графа Фазы 2 реализовано.

```bash
execweave validate run.jsonl
execweave graph run.jsonl
execweave graph-summary run.graph.json
```

Построитель графа не переинтерпретирует сырую телеметрию. Он использует семантику атрибуции и причинности, созданную Фазой 1.

## Схема графа

Текущая версия схемы графа:

```text
0.1
```

JSON-документ графа содержит:

```json
{
  "graph_schema_version": "0.1",
  "session_id": "...",
  "event_count": 100,
  "node_count": 24,
  "edge_count": 31,
  "nodes": [],
  "edges": []
}
```

## Узлы

Каждый уникальный идентификатор сущности Фазы 1 становится узлом графа.

Примеры:

```text
agent:Claude Code
session:<session-id>
process:<session-id>:1234
file:/repo/src/app.py
network_endpoint:1.2.3.4:443
executable:/usr/bin/python
```

Идентичность узла основана на идентификаторе сущности потока событий, а не на отображаемом имени.

Каждый узел накапливает:

- `type`
- `name`
- атрибуты сущности
- первую наблюдаемую временную метку
- последнюю наблюдаемую временную метку
- количество наблюдаемых событий
- типы событий, в которых присутствовала сущность

Сейчас Фаза 2 использует консервативное слияние атрибутов: существующий атрибут узла не перезаписывается незаметно более поздним конфликтующим значением.

## Рёбра

Событие, имеющее и источник, и цель, может породить направленное ребро графа:

```text
source --RELATION--> target
```

Например:

```text
session --LAUNCHED--> process
process --SPAWNED--> process
process --OPENED_READ--> file
process --CONNECTED_TO--> network_endpoint
```

Идентичность ребра — это кортеж:

```text
(source, relation, target)
```

Повторяющиеся события для одного и того же кортежа агрегируются в одно ребро, а не отображаются как дублирующиеся линии.

Агрегированное ребро хранит:

- точное число вхождений `count`
- первую/последнюю временную метку
- первый/последний номер последовательности
- идентификаторы подтверждающих событий
- участвующие типы событий
- backend(ы)
- метод(ы) атрибуции
- состояние причинности

Пример:

```text
process:p1 --OPENED_READ--> file:a.txt
count = 17
```

означает, что 17 событий Фазы 1 подтверждают одно и то же отношение графа.

## Агрегация причинности

Если все подтверждающие события каузальны:

```json
{"causal": true}
```

Если все они явно некаузальны:

```json
{"causal": false}
```

Если доказательства смешанные или не дают единого значения причинности:

```json
{"causal": null}
```

Слой графа не должен повышать некаузальную телеметрию до каузального отношения.

## События жизненного цикла

Некоторые события Фазы 1 имеют источник, но не имеют цели, например:

```text
process EXITED
session FINISHED_SESSION
```

Фаза 2 **не создаёт** для них фиктивный целевой узел или ребро к самому себе.

Вместо этого они вносят вклад в метаданные наблюдаемых событий исходного узла. Это сохраняет граф реляционным и не превращает каждое лог-событие в искусственный узел.

## Граница валидации графа

По умолчанию построение графа требует корректного и полного потока событий Фазы 1:

```bash
execweave graph run.jsonl
```

Для восстановления после инцидента или завершённой аварийно сессии агента:

```bash
execweave graph --allow-incomplete interrupted.jsonl
```

Поток всё равно должен быть структурно корректным; ослабляется только требование завершённой сессии.

## Сводка графа

```bash
execweave graph-summary run.graph.json
```

Сводка сообщает:

- количество событий
- количество узлов
- количество рёбер
- количества по типам узлов
- количества по отношениям
- количество каузальных рёбер
- количество некаузальных рёбер
- количество рёбер со смешанной/неизвестной причинностью

## Фильтрация

Создать уменьшенный граф, не изменяя исходный:

```bash
execweave graph-filter run.graph.json \
  --output causal.graph.json \
  --causal-only
```

Фильтр по отношению:

```bash
execweave graph-filter run.graph.json \
  --output network.graph.json \
  --relation CONNECTED_TO \
  --relation CONNECT_ATTEMPTED
```

Фильтр по типу узла:

```bash
execweave graph-filter run.graph.json \
  --output process-network.graph.json \
  --node-type process \
  --node-type network_endpoint
```

Фильтр по backend:

```bash
execweave graph-filter run.graph.json \
  --output syscall.graph.json \
  --backend strace
```

Фильтры можно комбинировать.

## Запросы направленных путей

Фаза 2 может запрашивать направленные пути времени выполнения:

```bash
execweave path run.graph.json \
  'session:abc' \
  'network_endpoint:1.2.3.4:443'
```

Ограничить рёбрами, чьи агрегированные доказательства каузальны:

```bash
execweave path run.graph.json SOURCE TARGET --causal-only
```

Ограничить отношения:

```bash
execweave path run.graph.json SOURCE TARGET \
  --relation LAUNCHED \
  --relation SPAWNED \
  --relation CONNECTED_TO
```

Поиск путей сейчас:

- направленный
- в ширину
- только простые пути (узел не может повторяться в одном возвращаемом пути)
- ограничен `--max-depth`
- ограничен `--max-paths`

Это не позволяет графу выполнения с циклами порождать неограниченное число результатов.

## Текущие критерии приёмки Фазы 2

- [x] Валидировать вход Фазы 1 до построения графа
- [x] Материализовать сущности в узлы
- [x] Дедуплицировать узлы по стабильному идентификатору сущности
- [x] Агрегировать повторяющиеся события `(source, relation, target)`
- [x] Сохранять доказательства событий на рёбрах
- [x] Сохранять семантику причинности
- [x] Сохранять первую/последнюю временную метаинформацию
- [x] Не создавать фиктивные рёбра для lifecycle-событий только с источником
- [x] Сводка графа
- [x] Фильтрация графа
- [x] Запрос направленного пути
- [ ] Улучшенное разрешение сущностей между семантически эквивалентными идентификаторами ресурсов
- [ ] Временные snapshot / фильтрация по временным окнам
- [ ] Компактная индексация доказательств для очень больших запусков
- [ ] Тесты миграции/версирования формата графа
- [ ] Интерактивный локальный интерфейс графа

Интерактивный интерфейс относится к Фазе 3. Он должен использовать этот контракт графа, а не читать сырые логи сборщика напрямую.
