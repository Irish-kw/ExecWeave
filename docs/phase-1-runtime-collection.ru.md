# Фаза 1 — Сбор данных времени выполнения

Фаза 1 формирует локальный поток событий времени выполнения, готовый для построения графа, который Фаза 2 может преобразовать в граф выполнения.

## Состояние

**Фаза 1 завершена для эталонного пути Linux и переносного резервного backend.**

ExecWeave теперь предоставляет два backend сбора:

- `strace` — сбор в Linux на основе системных вызовов. Захватывает короткоживущие дочерние процессы и действия с файловой системой/сетью, атрибутированные процессам на основании доказательств системных вызовов.
- `portable` — резервный вариант на psutil + watchdog для Linux, macOS и Windows. События процессов/сети собираются опросом; изменения файловой системы коррелируются с сессией и явно помечаются как некаузальные.

`auto` предпочитает `strace` в Linux, если он установлен, иначе выбирает `portable`.

```bash
execweave doctor
execweave run --backend auto -- claude
```

## Установка

```bash
git clone https://github.com/Irish-kw/ExecWeave.git
cd ExecWeave
python -m pip install -e ".[dev]"
```

В Debian/Ubuntu установите эталонный Linux-backend:

```bash
sudo apt-get install strace
```

Затем:

```bash
execweave run -- claude
execweave run -- codex
execweave run -- gemini
execweave run -- opencode
execweave run -- python my_agent.py
```

События записываются локально в:

```text
.execweave/runs/<session-id>.jsonl
```

Необработанные файлы `strace` по умолчанию удаляются после разбора. Сохраняйте их только для отладки:

```bash
execweave run --keep-native-trace -- claude
```

## Сквозная проверка Фазы 1

Запуск Фазы 1 можно проверить, ещё не строя граф Фазы 2:

```bash
execweave doctor
execweave run --output run.jsonl -- python my_agent.py
execweave validate run.jsonl
execweave benchmark --backend auto --iterations 5
```

`execweave validate` проверяет контракт потока событий, включая:

- корректные записи JSONL;
- один идентификатор сессии на файл;
- уникальные идентификаторы событий;
- непрерывные номера последовательности начиная с 1;
- корректные временные метки;
- обязательные поля событий/сущностей;
- ровно один `session.started` и один `session.finished` для завершённого запуска.

Для прерванного запуска, в котором законно отсутствует `session.finished`:

```bash
execweave validate --allow-incomplete run.jsonl
```

ExecWeave также по умолчанию отказывается повторно использовать существующий непустой выходной файл. Это не позволяет второму запуску незаметно добавить новую сессию с заново начавшейся нумерацией последовательности в тот же поток событий.

## Модель возможностей backend

### Linux-backend `strace`

Нативный эталонный backend Фазы 1 отслеживает потомков с помощью `strace -ff` и записывает рёбра, подтверждённые системными вызовами.

Он может создавать такие отношения:

```text
session --LAUNCHED--> process
process --SPAWNED--> process
process --EXECUTED--> executable
process --OPENED_READ--> file
process --OPENED_WRITE--> file
process --DELETED--> file
process --RENAMED_TO--> file
process --CHANGED_CWD_TO--> directory
process --CONNECTED_TO--> network_endpoint
process --CONNECT_ATTEMPTED--> network_endpoint
process --EXITED--> ...
```

Эти события включают:

```json
{
  "attribution": "syscall",
  "causal": true,
  "backend": "strace"
}
```

`OPENED_READ` и `OPENED_WRITE` описывают режим доступа, доказанный системным вызовом открытия. Они намеренно **не утверждают**, что позднее действительно был выполнен побайтовый `read()` или `write()`. Отслеживание потока данных на уровне байтов относится к будущему сборщику.

### Переносный backend

Переносный backend запускает команду напрямую и использует psutil/watchdog.

Он может создавать:

```text
session --LAUNCHED--> process
process --SPAWNED--> process
process --CONNECTED_TO--> network_endpoint
session --OBSERVED_FILE_CHANGE--> file
```

Изменения файловой системы остаются явными наблюдениями уровня сессии:

```json
{
  "attribution": "session_observation",
  "causal": false
}
```

Это предотвращает представление временной корреляции как каузальной атрибуции.

## Порядок и идентичность событий

JSONL sink добавляет каждому событию запуска монотонно возрастающий номер `sequence`. Временные метки сохраняются отдельно.

Переносные идентификаторы процессов используют PID + время создания процесса, поскольку операционные системы повторно используют PID.

Linux-backend системных вызовов ограничивает идентификаторы процессов сессией ExecWeave:

```text
process:<session-id>:<pid>
```

Поэтому идентичность процесса никогда не выводится глобально только из PID.

Парсер strace также выполняет предварительный проход по родительским связям процессов до формирования событий графа. Это предотвращает ошибочную маркировку дочернего процесса как корня сессии, когда запись трассировки ребёнка и запись `clone()`/`fork()` родителя имеют одинаковую временную метку в разных файлах трассировки.

## Короткоживущие процессы

Переносный backend может пропустить процесс, который полностью запускается и завершается между интервалами опроса.

Эталонный Linux-backend устраняет этот пробел Фазы 1, отслеживая системные вызовы процессов и потомков через `strace -ff`. CI содержит интеграционный тест, запускающий короткоживущий дочерний процесс и проверяющий появление ребра `SPAWNED`.

## Атрибуция путей файловой системы

Linux-парсер отслеживает рабочие каталоги каждого процесса и обрабатывает распространённые системные вызовы семейства `*at`. Относительные пути разрешаются по лучшим доступным доказательствам системных вызовов.

Для редких шаблонов dirfd атрибуция путей всё ещё может быть несовершенной. Исходные имена системных вызовов и пути сохраняются как атрибуты событий, чтобы downstream-потребители могли проверить, как было получено ребро.

## Сетевая атрибуция

Linux-backend записывает доказательства системного вызова `connect()` для:

- IPv4
- IPv6
- Unix-domain sockets

Успешные вызовы создают:

```text
process --CONNECTED_TO--> endpoint
```

Неудачные или асинхронные вызовы, включая распространённый неблокирующий случай `EINPROGRESS`, сохраняются как:

```text
process --CONNECT_ATTEMPTED--> endpoint
```

Событие сохраняет результат системного вызова и errno. Поэтому ExecWeave не сообщает ошибочно об асинхронной попытке подключения ни как о подтверждённом соединении, ни как об отсутствии сетевой активности.

Переносный backend использует инспекцию сокетов по процессам, когда операционная система предоставляет её текущему пользователю.

Отсутствие события никогда не следует трактовать как доказательство отсутствия сетевого действия у backend с недостаточными разрешениями или покрытием.

## Конфиденциальность

Телеметрия времени выполнения может содержать чувствительные пути, имена исполняемых файлов, аргументы команд и endpoints.

Фаза 1 использует следующие настройки по умолчанию:

- все данные событий остаются локальными;
- необработанные файлы трассировки системных вызовов удаляются после разбора, если не указан `--keep-native-trace`;
- содержимое файлов не трассируется;
- байтовые буферы из `read()`/`write()` не собираются;
- аргументы `execve` не копируются в события графа, кроме количества аргументов.

Обёртка сессии всё же записывает команду, переданную ExecWeave, поэтому пользователям не следует размещать секреты непосредственно в командной строке.

## Диагностика

```bash
execweave doctor
```

Пример:

```json
{
  "auto_selected": "strace",
  "platform": "linux",
  "portable": true,
  "strace": true
}
```

## Benchmark накладных расходов

Фаза 1 включает повторяемый smoke benchmark:

```bash
execweave benchmark --backend portable --iterations 5
execweave benchmark --backend strace --iterations 5
```

или:

```bash
python benchmarks/phase1_overhead.py
```

Он сообщает исходные baseline/instrumented времена, медианы и коэффициент накладных расходов. Это измерения, зависящие от среды, а не опубликованное заявление о производительности.

## Контракт CI

Матрица GitHub Actions запускается в Linux, macOS и Windows с поддерживаемыми версиями Python.

Помимо unit-тестов и linting, CI теперь выполняет:

1. `execweave doctor`;
2. сквозной переносный запуск;
3. `execweave validate` для этого переносного потока;
4. сквозной Linux-`strace`-запуск;
5. валидацию нативного Linux-потока;
6. smoke-тест benchmark Фазы 1.

Это означает, что Фаза 1 тестируется как реальный CLI-workflow, а не только как изолированные Python-функции.

## Явно вне Фазы 1

Следующие возможности остаются будущей работой и не помечаются ошибочно как завершённые:

- Windows ETW backend с атрибуцией файловой системы процессам
- macOS Endpoint Security backend с атрибуцией процессам
- Linux eBPF backend для снижения накладных расходов ptrace
- корреляция DNS с доменами
- побайтовое отслеживание потока данных read/write
- семантическая телеметрия agent/tool/MCP
- материализация графа и интерактивная визуализация

Эти возможности могут использовать ту же модель событий без изменения контракта Фазы 1.

## Почему `strace` раньше eBPF?

Фазе 1 нужна ориентированная на корректность эталонная реализация атрибуции процесс/файл/сеть и семантики событий. `strace` легко инспектировать и тестировать, и он захватывает короткоживущих потомков без выдумывания причинности.

Backend eBPF — естественная следующая оптимизация для снижения накладных расходов и постоянного сбора, но он должен реализовывать ту же семантику событий графа, а не неявно определять новую.

## Участие в разработке

Особенно полезны следующие вклады: Linux eBPF, Windows ETW, macOS Endpoint Security, разрешение путей/сущностей, оценка накладных расходов, конфиденциальность/редактирование и воспроизводимые нагрузки агентов.

Для нового backend сбора сохраняйте различие между доказанной каузальной атрибуцией и наблюдением на уровне сессии.
