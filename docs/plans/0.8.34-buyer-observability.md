## 0. 買方目標與交付界線

如果我是付出幾百萬元的採購者，我買的不是會動的 graph，也不是事件數量。我需要在不讀原始碼、不挖 JSON、不請作者提示路徑的情況下，獨立確認一次執行的內容、責任、結果與證據缺口。

必須回答：

1. 這次要做什麼？有哪些業務角色？目前在哪一步？
2. 每個 agent 收到什麼、回答什麼、使用哪次模型與工具？
3. 哪一個可見輸入、呼叫、重試或交接對應最後的結果？不能猜測隱藏思考。
4. A 把什麼交给 B？只是指定收件者，還是真的交付或消費？
5. 哪一步失敗？Agent 自述與實際測試結果是否矛盾？
6. 它接觸哪些 process、file、network？歸屬是精確證據還是僅有關聯？
7. 匯出交給另一個人後，是否仍能讀到相同內容與限制？

禁止把「資料其實有存，你自己找檔案」當成產品完成。禁止把所有測試綠燈或單一完整度百分比當成買方驗收。

### 授權與不變條件

- 只在工作分支做可回退、非 force 的提交。寫入前重查遠端 branch/main，避免覆蓋其他人的更新。
- 本階段不 merge、不 tag、不 release、不提升套件版號、不自行關閉外部追蹤議題。
- 不更改上游 CAMEL、AutoGen、MetaGPT 的任務／SOP 行為來讓展示更好看。
- 不製造 sender、recipient、delivery、consumer、model owner、hidden reasoning 或缺失的內容。
- 原始事件、內容 hash、原生身份與錯誤結果不得為了展示而改寫。
- 不公開真實使用者對話、raw capture、秘密或原始截圖；回歸資料須去識別或明示合成。
- 不把未執行的測試記成 PASS；區分合成契約、舊錄製重播、真實新錄製與買方操作。

## 1. 問題來源與證據界線

買方問題來源：Irish-kw/ChatGPT2GrokBot #75、#76、#77、#78、#79、#80；總追蹤 #81。這些是另一個 repository 的 issue，不是 ExecWeave 同號 issue。

- #75：SUCCESS/FINISHED，但 agent TASK/RESPONSE 空白、控制字串或只有檔名。
- #76：Model node 只呈現 metadata，缺少可操作的 prompt/completion 瀏覽。
- #77：MESSAGE/Tool 只有 routing/count，正文讀取斷裂。
- #78：預設圖被基礎設施活動淹沒，角色主線難找。
- #79：跨 provider 的閱讀與缺口判斷不一致。
- #80：Artifact 只有檔名或 file://，沒有執行當時內容的內嵌預覽。

問題來源連結：https://github.com/Irish-kw/ChatGPT2GrokBot/issues/81

先前 #70 的 capture=100% 不能成為本 PR 的前提：其分母包含未驗證的 live/finished parity，部分來源與捕捉對照引用同一 semantic ledger。「未驗證」不等於「provider 不提供」。逐項確認來源、設定、捕捉、解析、儲存、展示與封存，才能定位缺口。

### 原始碼已確認的重點

| 路徑 | 現況 | 本版不能誤判的地方 |
|---|---|---|
| `viewer_agent_panel.py` | Tool occurrence 可顯示 archived_reference；model history 依赖 viewer_inference_occurrences | 有引用不等於正文可讀；不是單純再新增空面板 |
| `viewer_agent_panel_default.py` | Task/Thinking/Response 通用整理；Response 選最後一筆 | 控制訊息可能壓過交付；Thinking 不應成為必填 |
| `conversation_records.py` | Codex >80 則預覽取前10/後70；Ollama/AGY 有不同還原路徑 | 初始預覽限制不應變成不可找回的中間歷史 |
| `viewer_semantic_projection.py` | 模型預覽4,000字元、任務折入agent、owner fallback及unresolved metadata | 預覽不等於全文；latest task不等於所有task；未知owner不能被洗成已知 |
| `content_store.py`、`live.py` | 已有hash內容儲存、認證與run-local內容讀取 | 優先重用；不要新增任意路徑讀檔服務 |
| `finalization.py` | 必要檔案為graph/viewer/conversations | 不足以證明所有正文引用都隨包完整交付 |
| `dashboard_shell.py`、`_dashboard_shell_base.py` | 多層注入與精確字串接點 | 共用元件小步整合；不要堆更多脆弱替換或一次重寫全部 |

上述是源碼路徑判讀，不代表已重新重現每個 provider 的真實失敗。本 PR 後續進度必須另外记录每一批實測。

## 2. 改善工作包

### W01：三種狀態分離（P0）

使用者看到三個獨立區域：

- 執行：running / succeeded / failed / interrupted / collector_failed / unknown。
- 任務：unverified / agent_claimed_complete / tests_passed / tests_failed / missing_deliverable。
- 觀測與交付：內容缺口、歸屬缺口、最後同步、封存完整性。

程序exit=0、agent說完成、測試通過、資料完整是不同事情。0個測試的成功退出不能算任務驗證成功。舊資料缺欄位顯示unknown，不能回填PASS。必須保留原始collector錯誤，次要匯出錯誤不得遮蔽。

驗收：同時正確展示「程序成功、任務未驗證、兩筆tool結果缺失」；以及「任務失敗、證據完整且可定位根因」。

### W02：所有面板共用正文讀取（P0，第一批垂直切片）

Message、model request/response、tool input/output及artifact共用內容讀取契約，支援預覽、展開、搜尋、複製、取消、缺檔與完整性結果。

每份內容攜帶run、事件/occurrence、來源、owner證據、hash、大小、型態、觀測時間、representation與完整度。分開capture completeness、preview truncation、retrieval status、verification status與redaction。

安全條件：

- 只解析run已登錄的`content/sha256/<hash>.<json|txt|bin>`引用；不得接受任意file://、絕對路徑、../、跨run或遠端URL。
- 重用既有Live認證與目錄限制。沒有token不可讀，不能把token放入外連或分享內容。
- 預設純文字呈現，不執行HTML/script，不載入遠端圖片或自動導航。
- 不將未驗證的bytes標成hash verified；失敗或不能驗證要明說。
- 大內容按需讀取、限制記憶體與DOM、可取消；不能靠不告知地刪除內容達成效能。
- 相同hash可共用bytes，但call/owner身份仍各自存在；跨run不共用敏感快取。

第一批打通「一筆真實形狀的tool content reference → 產品內讀取 → 預覽/錯誤 → 可測試」；未完成Offline/全provider前不得宣稱W02整項完成。

### W03：Agent完整工作歷史（P0）

可定位「任務→收到的上下文→可見輸出→模型交換→工具→訊息交接→交付物」。Task/Response僅是摘要。

- 控制token保留原文，另分類為control；不能當成唯一交付，也不能自動升格前一句為已驗證final。
- Thinking只顯示來源明確提供的可見說明；沒有不是故障，禁止生成填補。
- 中間歷史可分頁、搜尋、跳轉；200輪以上仍可查指定第83輪。
- 相同文字在不同occurrence不能去重成一筆；request累積歷史不等於新的assistant response。
- 不借用root/sibling/shared model內容填空；同名agent与兩個/root必須隔離。
- 使用者打開舊輪次，新事件不能收合、跳頁、捲到底或切換owner。

### W04：Model/Tool逐次調查（P0）

Model每次call顯示requesting agent、模型、實際觀測request/response、時間/狀態、錯誤、重試及來源。Hook收到的user prompt不冒充送到模型的完整request。用量/成本沒有可靠來源就unknown。

Tool顯示每次arguments/result、錯誤/exit、時間及有證據的process/file/network關聯。`x25`應開啟25次呼叫清單。空字串、null、未提供、未啟用、缺檔、截斷與遮罩不能混在一起。

共用model/tool不能合併不同call；未知owner保留可見入口。聚合只改展示，所有occurrence能反查原始事件。

### W05：訊息與產物交接（P0）

Sent、addressed、delivered、consumed分開且各有證據。Message正文與上下文可讀，consumer不由時間或共用檔案推測。

Artifact需顯示執行當時snapshot、producer、觀測時間、hash、來源事件、有證據的consumer與lineage。同名不同版本不得混合。

优先讀captured snapshot。事後讀workspace只能明示「現在讀取的版本」，不能冒充歷史證據；不能僅因正文出現路徑就自動讀檔。沒有歷史內容時明示無法重建。

### W06：預設工作流程與OS證據互通（P0基本可用；視覺微調P1）

三個工作區：工作流程（任務/角色/訊息摘要/重要產物）、調查（可搜尋時間線）、執行證據（process/file/network/provider/未歸屬）。

- 角色列表與搜尋不依賴畫布；無需先學pan/zoom才能找到agent。
- 重要錯誤與未歸屬項目不能被折疊藏掉；折疊顯示數量且可展開。
- 不把/root固定當噪音，它可能就是業務角色。
- 不把每則message都畫成永久節點；用可展開交接聚合避免另一個hairball。
- agent/tool到OS證據一步可達；不要犧牲產品原有差異性。
- Fit針對使用者明確選擇的可見範圍；不能標全圖卻暗中裁切。使用者操作後不強搶camera。
- 所有view-only聚合保留原始node/edge映射、計數、選取与可追溯來源。

### W07：分項健康與跨provider契約（P0）

呈現訊息正文X/Y、模型request/response X/Y、tool input/result X/Y、snapshot存在且驗證X/Y、未知owner/delivery/consumer數量、最後同步與封存狀態。

分母是明確定義且版本化的已知項目，不是全世界的真實recall。端到端recall只在有獨立ground truth的實驗中計算；不能用自身輸出當分母。

缺口原因包括not_exposed（需要來源證明）、capture_disabled、unsupported_parser、capture_failed、missing_blob、hash_mismatch、preview_only、not_verified、unknown。不能把未測或本地缺檔歸咎provider。

跨provider保證同一種閱讀與限制說明，不承諾每個來源暴露同樣資料。Metadata-only是使用者選擇，不能誤判為recorder failure。

### W08：Live/Finished/Offline交付鏈（P0）

同一renderer與內容契約，完成時最後權威同步成功才視為同步；失敗可見且能手動retry。停止polling本身不是成功。

封存檢查reference closure：所有宣稱包含的內容引用存在、大小/hash一致、已隨包交付；在另一台機器且原server關閉時可讀。主要三個檔案存在不夠。

支援舊資料但不改原始版號；缺欄位unknown。Original evidence與redacted sharing export分開；遮罩產物用新hash、記錄衍生關係，禁止修改原始bytes後仍宣稱原hash。

| 改動 | 主要接點 | 必須一起處理的影響/回歸 |
|---|---|---|
| 正文resolver | content_store、conversation core、live、agent/model/tool面板 | 認證、run隔離、路徑越界、hash、missing、空值、長內容、HTML、Offline |

| Call正規化 | semantic projection、adapter/runtime、panel | 共用model/tool、未知owner、stream/retry、每次配對、聚合計數 |
| Task/artifact | framework task folding、內容索引、adapters | 最新覆蓋歷史、同名版本、producer/consumer推論、事後檔案冒充snapshot |
| 預設圖/layout | viewer projection、execution flow、layout、camera | raw映射、orphan入口、選取、Fit、GIF、large-run protection、效能 |

| 展開/搜尋/捲動 | viewer_fold_state、refresh、所有內容面板 | 新事件干擾閱讀、切node/換run/reload狀態串線、blocked storage |

三項守恆：證據守恆、身份守恆、狀態守恆。任何display-only改動都不得把unknown/failed/unverified升級成proven/success。

## 4. 實作與回退順序

A. 固定已知失敗案例：核對版本、hash、缺件；建紅燈測試；真實回放與合成fixture分開。

B. 一條垂直路徑：先一筆tool正文，從引用、安全讀取、顯示、錯誤、Live直到Offline；同一套元件再擴充model/message/artifact。不能一次做四個仍然只有檔名的面板。

C. 歷史與身份正規化：多輪、多任務、shared calls、重試、same text。證明缺口在collector時才定點修它。

D. 交接、產物、搜尋、工作流程：正文正確後再改布局，讓資料與視覺問題可獨立定位。

E. 封存與買方驗收：舊資料、clean wheel、三OS、真provider、異地Offline與獨立操作。

每批一個可識別commit，附改動/未做/測試/影響範圍。回退只revert該批，不force、不刪raw、不在main做實驗。共用schema採additive reader compatibility，必要時feature開關；不得以開關掩盖required gate。

## 5. 驗證矩陣

### 驗證種類

- Synthetic contract：只證明特定資料形狀及邊界，不能替代實際來源暴露能力。
- Historical replay：只證明新版呈現既有內容，不能證明新捕捉。
- Fresh real capture：指定OS、provider與版本的端到端證據；不得外推所有平台。
- Buyer-only journey：不看raw、不靠作者完成調查；不能替代程式正確性測試。

### 不得縮小的範圍

Windows、Linux、macOS；Live、finished原頁、server仍在的重新開啟、server關閉的Offline。13類既有provider契約保留：Claude、Codex、AGY、Cursor、OpenCode、Ollama、llama.cpp、vLLM、LM Studio、Anthropic、OpenRouter、LiteLLM、OpenAI-compatible。三個framework包括CAMEL、AutoGen、MetaGPT；native session及metadata-only也必須測。

平台/provider原生不支援或未取得授權時記BLOCKED/NOT_RUN及原因，不能用fixture宣稱fresh PASS。

### 必測案例

| 編號 | 案例 | 驗收 |
|---|---|---|
| B01 | 正常程序但任務無證據 | 不宣稱任務成功 |
| B02 | Agent說完成、測試失敗或0tests | 自述与事實並列 |
| B03 | 每角色輸入/輸出 | 不離開Dashboard可讀 |
| B04 | terminal control token | 歷史保留、交付另列 |
| B05 | 同名agent、兩個/root | 不串線 |
| B06 | shared model/tool | 每次owner與call可查 |
| B07 | 200輪、長正文、same-text turns | 中間與尾部可找回、不同occurrence保留 |
| B08 | 舊輪次展開後新事件 | 不收合、不跳頁、不搶scroll/camera |
| B09 | sent但沒有received | delivery未確認 |
| B10 | 只看到檔名/同檔名不同版本 | snapshot或明示缺失，不讀現在版本冒充 |

| B22 | 分享遮罩包 | 衍生hash、無秘密、不改原始證據 |

### 操作與效能目標（待量測，不是已有成績）

固定参考案例：30秒內辨識任務/角色/狀態/缺口；60秒內找到指定回答或呼叫；從面板到對應正文至多三次操作。

固定硬體/瀏覽器，參考負載10 agents、1,000 calls、10,000 events、50MB内容：首屏可操作≤3秒，小內容展開p95≤500ms；大內容可取消且不凍結。不能靠靜默刪資料達標。
